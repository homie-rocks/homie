# Stripe connection: design and evidence

Researched 2026-10-08 against Stripe's fetched documentation, CLI source and public OpenAPI. The login/credential files were also fetched at the release tag and matched master byte-for-byte. Latest CLI release fetched from GitHub: **v1.53.1, 2026-10-07**; public API schema: **2026-09-30.endive**.

## Design: what can actually ship

**No generally available, documented backend-credential provisioning flow found meets all of one browser approval, an independently running Cloudflare Worker using Stripe’s normal payment API, and no platform/operator credentials for live payments.** Do not promise otherwise. Current CLI OAuth is not a server API key provisioning interface. The older CLI's test key is a useful conditional bridge, not a production credential strategy. Never downgrade Stripe or reproduce its private pairing protocol to force that bridge.

1. The person says “add a shop”. The AI creates shop.json, keeps the studio's choices, and runs `stripe_login` (CLI: `homie-studio shop connect`). If Stripe CLI is absent the result gives the AI `npm install -g @stripe/cli@latest`. No key is requested in chat.
2. The toolkit uses an isolated Stripe CLI profile for this studio. Stripe's own `login --non-interactive` produces a browser URL and pairing code. The toolkit accepts Stripe’s production Dashboard and access.stripe.com verification URLs, opens that URL and runs the allowlisted completion command using argv, not a shell. The person selects their own account/sandbox and approves on Stripe. New owners register/verify their account in Stripe; account activation, business/bank/identity details and Stripe's access controls may require additional Stripe steps. These are not Homie rules.
3. The toolkit probes the session and captures only a test API key exposed by the official CLI's `config --list`, privately in memory. Legacy pairing issues restricted keys expiring after 90 days; their scopes are chosen by Stripe, not narrowed by Homie. There is no public create-RAK API to replace these with a custom minimal key. Current OAuth may expose no such key: return `worker-credential`, explain the gap, and leave the shop closed. Do not extract the CLI’s private OAuth refresh token or make checkout depend on the desktop agent. A separate MCP runtime is discussed below; it is not implemented here.
4. Cloudflare must already have a deployed HTTPS address before webhook creation. If connection starts first, finish Stripe approval and return “deploy your studio, then run shop connect again”; reuse that profile afterwards. If Cloudflare is not connected, `cloudflare_login`, one separate Cloudflare approval, then `studio_deploy`. A configured domain is not proof of deployment: the AI must check the deploy result. No webhook points at localhost.
5. With a usable test key, validate access with a read, create the endpoint at `<site>/api/shop/hook`, capture its signing secret, and write the pair in one `wrangler secret bulk` call over stdin. No credentials enter tool results, command arguments or Homie services. List all existing endpoints; reuse the recorded endpoint when it still matches and the stored connection is unchanged. On renewal or lost local state, create a replacement because Stripe returns its signing secret only on creation. Disable only older Homie-created endpoints for that exact URL after the new pair is saved. A failed save leaves old endpoints active and allows retry.
6. The AI can make Products/Prices through Stripe's official CLI or optional MCP, using the existing `shop catalog` reconciliation. Inline product data already works without a separate catalog. Verify a purchase on the deployed test shop with Stripe's test card, signed webhook delivery, item grant and office refund/revocation. “Secrets installed” is **not** this end-to-end verification; report that acceptance as the next step. This checkout's tests use a stand-in Stripe and real local browser, never a real account.
7. When the person says “go live”, use `shop connect --live`. Do not export a redacted live CLI key or assume live writes are enabled. The implemented flow names the unsupported credential step. The closest generally available independent live path is **the owner explicitly chooses `shop connect --manual --live`, creates a restricted live key in Stripe's Dashboard, and pastes it into the loopback page**. The page creates the webhook and sends both secrets directly to the Worker. This is exactly the remaining manual step and fails the owner's never-see-a-key target. Do not silently switch to it or ask for a key in chat. Then reconcile the live catalog and verify a real purchase/refund only with the owner's authorization. Stripe account activation remains Stripe's own requirement.
8. Rerun connect to check/renew. Legacy expiry or an authentication failure starts another browser approval; a valid session is reused. CLI OAuth refreshes its own session silently, but this does not refresh the Worker's API key. Return the recorded expiry and renewal command, including when connection is already installed. No background service or silently renewed long-lived legacy key is claimed. Manually supplied keys follow the owner's Stripe expiry/rotation settings and are renewed with the chosen fallback.

## MCP OAuth runtime caveat

The fetched [protected-resource metadata](https://mcp.stripe.com/.well-known/oauth-protected-resource) identifies
`https://mcp.stripe.com` as the resource and scope `mcp`. Its [authorization-server metadata](https://mcp.stripe.com/.well-known/oauth-authorization-server)
advertises dynamic client registration, authorization code and refresh-token grants, S256 PKCE, and token-endpoint
authentication `none`. Thus a studio-owned MCP client can authenticate without any Homie service or client secret.
**An LLM/desktop agent need not inherently be present for every MCP call.** This is not a claim that OAuth or
MCP makes independent execution technically impossible.

Using that user session for every production checkout would instead make the Worker a persistent MCP client,
with token storage/rotation and tool-response handling replacing its normal Stripe API transport. It would not
provision the backend API key this toolkit uses. Stripe's [current guidance](https://docs.stripe.com/mcp) recommends
agent API keys for independent, persistent application access and documents mandatory human confirmation for
some MCP financial writes, including refunds. Its [architecture guide](https://docs.stripe.com/agents/how-it-works)
places MCP/CLI among tools for building integrations, distinct from the application's billing/commerce runtime.
This research did not establish that routing the entire shop through a user-scoped MCP session is a supported,
recommended production payment architecture. It is **an unverified alternative runtime design**, not a proven
one-approval credential solution; this change does not silently introduce it. No authenticated schema or live
behavior was tested, in accordance with the no-real-account constraint. This is an evidence boundary, not a
claim that Stripe explicitly forbids such a client.

## Local implementation evidence and boundaries

`packages/studio/lib/cloudflare.mjs:runner` executes the studio's Wrangler in `site/`, preserving its existing Cloudflare authentication (including optional Stripe Projects credentials), with secrets on standard input. Existing `lib/shop.mjs` uses `secret put`; the new browser-credential path uses `secret bulk` to update both values together. Wrangler output is consumed privately. The current [Wrangler secret bulk reference](https://developers.cloudflare.com/workers/wrangler/commands/workers/#secret-bulk) documents stdin JSON input and creating a new deployment; this changes secrets on the studio’s Worker, not on a Homie service. A non-secret receipt outside the checkout records mode, expiry, endpoint and a credential fingerprint, not secret values. Stripe itself owns its CLI credential storage (legacy test config is plaintext; newer OAuth uses secure credential storage when available).

Research fetched: the linked Markdown docs; CLI `pkg/cmd/login.go`, `pkg/login/login.go`, `pkg/login/oauth_credentials.go`, `pkg/login/keys/polling.go`, `pkg/config/profile.go`, `pkg/config/config.go`, generated resources and hidden `keys_permissions.go`; the Stripe AI README; public OpenAPI JSON. No Stripe/Cloudflare sign-in, private API, keychain extraction or real payment used. Live capability and permission choices have not been account-tested. Documentation and master source differ on whether repeat login reauthorizes; implementation probes first and only logs in when required.
