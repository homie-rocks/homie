# Apps in a Homie studio

Design written before implementation, 2026-10-08.

1. An app is one transforming screen, its roles, and the parts in that screen. It can use every engine package a game uses. No rounds, scores, bots, or page navigation are required.
2. Source lives in `apps/<id>/app.json`, `index.html`, and `src/`. IDs share the site's namespace with games and cannot collide. A common experience discovery function feeds the existing build, dev, deployment, parts, shop and standalone machinery; games retain their existing metadata and output paths.
3. `app.json` declares name, blurb, entry, roles (`can`, `signIn`), surfaces (`phone`, `wall`, `kiosk`, `tablet` mapped to roles), wording (`open`, `join`, `one`, `many`), records, parts, and optional standalone settings. The phone surface's role is the default, falling back to the first public role. Role names describe people, not netplay host/replica responsibilities.
4. `/<id>/` is the app's landing, `/<id>/open` its screen, and `/<id>/tv` the existing wall shell. Public role/surface parameters select a presentation. Staff access uses an unpredictable address issued by the owner plus an existing signed-in account with a role grant (the owner may act in every role). Every privileged operation rechecks authorization; neither a URL parameter nor browser hosting confers permission.
5. The server-hosted saves described in `docs/rooms-slice-2-notes.md` recover matches but intentionally expire on empty-room end. Permanent operational records therefore use the studio's existing D1 through a small documented records helper, with declared collection permissions, bounded JSON, optimistic versions and durable deletion. No separate database service or socket protocol. Room checkpoints remain suitable for transient scene state.
6. The existing sandbox shell bridges record requests to same-origin HTTP with the browser's account. Record permissions are enforced in the Worker, not in UI or host code. Roles may read, create, update or delete only declared collections. App authors must separate public and private collections; a filtered HUD is never data isolation. The existing netplay carries the shared scene; record refreshes recover missed notices and reconnects.
7. `dev --lan` binds to all interfaces and prints real Wi-Fi addresses. Opening that address gives the existing TV QR a reachable target. Loopback remains the default. Passkeys require HTTPS or localhost: LAN HTTP does not acquire a fake production sign-in bypass. Browser proof may provision local test accounts explicitly.
8. Public `links` helpers reuse the existing QR encoder, accept an address plus parameters, and create cryptographic IDs using `getRandomValues` even on plain HTTP. Private role tokens are never copied into customer ticket links or public manifests.
9. A welcome queue starter shows a sculptural 3D scene that changes around customer, wall and staff roles: join, see a numbered ticket, call the next person. Existing netplay, engine packages, native accessible controls and reduced motion; no invented customer activity. App checks exercise declared real UI actions across simultaneous surfaces and reload/reconnect, rather than requiring a round.
10. Standalone wraps the same app bundle through the existing desktop/mobile build. Its customer role can use public app records; staff sign-in and native store billing are outside the existing wrapper's capability. Parts extend to app components, music loops/stems/tracks and video intros/templates, with explicit intended uses and licences; sharing stays independent of any future price.

## Compatibility and verification

Keep the internal `games.json` catalogue and built `games/<id>` asset namespace as compatibility plumbing, discriminating app rows with `kind: app`; public listings expose apps separately. Do not rewrite old game bundles or add app fields to game-only output. Reuse play/tv/watch and Table/Lobby, not an app socket server. App metadata is validated before building. The app skill and generated AGENTS guidance teach a single scene with contextual panels, roles and composable parts, with the fewest decisions required from the human.

Tests cover discovery and collisions, the scaffold/MCP command, unchanged game builds, routes and copy, record permissions and conflicts, private links, LAN binding, HTTP IDs and QR targets, app check and standalone preparation. Real Chrome proof opens a wall, two phones and a staff tablet on a fresh local studio. All required gates run one suite at a time. No deployment, push or pull request. Stop work below 3 GB free.
