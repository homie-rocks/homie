# Room lifecycle

Tables stop simulation timers between settled rounds and retain the next-round deadline in their alarm. Public player and watch sockets use WebSocket hibernation. Restoring a socket restores its authenticated context and rate state; a refused restore closes the transport so the client can reconnect.

Gates multiplex live traffic over a WebSocket. At an idle boundary the Table detaches that internal connection without closing player sockets. Each new Gate link owns a fresh sequence epoch. Ordered HTTP input and a temporary output stream cross the boundary; live rounds reconnect the multiplex socket. Client edge heartbeats preserve transport liveness throughout idle breaks without waking an object. Live rounds, visibility changes, and a missed next-round deadline use clock pings; an unanswered clock ping still detects a dead room. Transient binding failures retry in order with capped exponential backoff. Output backpressure preserves the session; a logical failure removes the Table relay and tells the Gate to reconnect players.

Session storage uses an explicit field allowlist and individual relay-client rows with URL differences relative to their Gate. Simulation snapshots remain in the existing host save. Chat state is written only when changed and statistics flush at most once a minute. Watcher addresses are digested for admission limits, user agents are reduced to the QA classification, and orphan request records are removed on restoration.

Quiet public matchmaking refills open rooms across all pools before opening shard zero. Sixteen entry objects own player reservations and lease eight routing decisions at a time from a per-game policy object. The policy counts consumed decisions over one second and spreads traffic above 128 observed joins per second; one-second leases let traffic consolidate when demand falls. Persisted 20-second route ownership keeps retries on their original shard across load changes and entry eviction. Invitations use the selected room directly. Public room numbers identify their shard; named-server pools keep their room cap in one shard. A short-lived player reservation makes concurrent retries idempotent. Room reports retire fulfilled seat holds while preserving retry ownership, so eviction does not count seated players twice. Reads aggregate shard counts, and queued room summaries paginate in game-key order. A separate per-game peak object combines the latest timestamped shard totals, excludes expired observations, and persists only rising peaks, coalesced over one second. Current shard totals remain volatile; restored historical peaks are never reused as current occupancy. It receives room reports, not joins. Independent historical shard peaks are never added.

This follows Cloudflare’s [coordination and sharding guidance](https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/): reservation ownership and room bookkeeping are distributed, and the matching-policy coordinator receives one request per lease rather than per player. [WebSocket auto-responses](https://developers.cloudflare.com/durable-objects/api/state/#setwebsocketautoresponse) answer idle heartbeats without JavaScript execution.

The [throwaway lifecycle fixture](../packages/studio/test/fixtures/room-lifecycle/README.md) exercises real Worker routing, Tables, Gates, and external WebSockets. Deployment measurements and cleanup results belong in the pull request description, not in the toolkit source tree.
